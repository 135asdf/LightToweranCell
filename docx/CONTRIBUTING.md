# 冲刺史莱姆 — 日常工作要求

本文件是团队的日常协作规范,所有合作者(包括仓库负责人)必须遵守。遇到不明确的地方,先在群里沟通再动手。

> **协作模式**:本仓库**推荐**采用「**分支 + Pull Request(PR)**」模式:每次任务在独立分支上完成,通过 PR 由负责人审核后合并到 `main`。**需要说明**:因仓库为 GitHub 免费版的私有仓库,**`main` 分支没有开启技术层面的强制保护**(免费私有仓库不支持分支保护规则),所以"必须先走 PR"目前是靠**团队自觉遵守**来保证的,不是 GitHub 强制拦截。负责人会定期检查提交记录,违规直接 push 到 `main` 的提交会被要求修正。请大家把 PR 流程当作纪律执行,这是保护主体版本稳定的唯一防线。

---

## 一、每日固定流程

1. **开工前先 pull**:写任何代码之前,执行 `git pull`,确保基于最新代码工作。
2. **先说明再动手**:今天要动哪些文件,开工时在群里说一句,避免撞车。
3. **在分支上工作**:永远不要直接在 `main` 上改代码,每次任务新建一个分支(见第三节)。
4. **小步提交**:每完成一个独立的小改动就提交一次,不要攒一大堆再一次性提交。
5. **自测**:涉及物理、碰撞、关卡、敌人的改动,必须运行 `tests/` 下相关测试场景确认没有改坏别的东西。
6. **收工检查**:当天所有改动必须已经 push 到自己的分支,并提交了 PR(或 PR 已合并);在群里简单汇报今天改了什么、明天计划做什么。

---

## 二、提交信息规范

格式:**`类型: 一句话说明`**(用中文,说清"改了什么、为什么")

常用类型:

| 类型 | 用途 | 示例 |
|---|---|---|
| `feat:` | 新功能 | `feat: 新增第二关的移动平台` |
| `fix:` | 修复 bug | `fix: 修复箱子被顶起后卡在墙里的问题` |
| `refactor:` | 重构不改行为 | `refactor: 抽取敌人移动逻辑到基类` |
| `docs:` | 文档 | `docs: 更新游戏设计文档` |
| `test:` | 测试 | `test: 新增箱子碰撞回归测试` |
| `perf:` | 性能优化 | `perf: 减少瓦片地图加载耗时` |

要求:

- 一次提交只做一件事。
- 不要用 `update`、`修改`、`asdf` 这种无意义的信息。
- 提交前用 `git status` 检查,**只提交本次相关的文件**。

---

## 三、PR 协作流程(核心)

### 3.1 合作者:如何提交一次改动

每次任务走一遍下面的流程:

```bash
git pull                                # ① 拉取最新的 main
git checkout -b fix/修复标题             # ② 新建自己的分支(名字见下方规范)
# ……在 Godot 里修改、保存,跑相关 tests/ 自测……
git add .
git commit -m "fix: 修复第二关平台间隙过大的问题"
git pull --rebase origin main           # ③ 把 main 的最新代码合进自己的分支,提前解决冲突
git push -u origin fix/修复标题         # ④ 推送到远程自己的分支
```

推送成功后,**在 GitHub 网页提交 PR**:

1. 回到仓库主页,会看到黄色提示条 **Compare & pull request**,点它;也可以到 **Pull requests → New pull request**。
2. 确认合并方向:**base: main ← compare: 你的分支**。
3. 标题沿用提交规范格式(如 `feat: 新增蜜蜂敌人`),描述写清三件事:
   - **改了什么**
   - **为什么改**
   - **怎么测试的**(跑过哪些 `tests/` 场景、自己玩过哪关)
4. 点 **Create pull request**,然后在群里 @负责人 提醒审核。

**分支命名规范**:

| 类型 | 分支名示例 |
|---|---|
| 新功能 | `feature/bee-enemy` |
| 修 bug | `fix/level2-platform-gap` |
| 文档 | `docs/update-contributing` |
| 测试 | `test/box-collision` |

### 3.2 负责人:如何审核并合并 PR

1. 打开仓库 **Pull requests** 列表,进入合作者提交的 PR。
2. 点 **Files changed** 逐文件查看改动,重点检查:
   - 是否动了公共文件(`project.godot`、`autoload/`、共享 `data/`)
   - 是否符合提交规范、有没有夹带无关文件(如 `.godot/`、临时文件)
   - 涉及物理/关卡的改动,描述里是否说明了测试情况
3. 有问题的:点 **Review changes → Request changes**,写明修改意见,退回给合作者改;合作者改完 push 后 PR 会自动更新。
4. 没问题的:点 **Review changes → Approve**,然后 **Merge pull request → Confirm merge**。
5. 合并后点 **Delete branch** 删掉合作者的分支(保持仓库整洁)。

### 3.3 PR 规范

- **一个 PR 只做一件事**,不要混着改多个不相关的东西。
- 描述必须写清「改了什么、为什么、怎么测」,说不清的不允许合并。
- 涉及物理、碰撞、关卡、敌人的 PR,必须在描述中注明已跑过哪些 `tests/`。
- **负责人不得合并自己没验证过的 PR**;自己改代码时同样要开分支、提 PR,让合作者(或至少自己按清单)review 一遍。

---

## 四、分工与文件避让

- 按 `scenes/` 下的子目录分工,例如:甲管 `scenes/enemies/`、乙管 `scenes/level/`、丙管 `scenes/ui/`。
- **不要同时编辑同一个文件**,尤其是 `.tscn` 场景文件,它们最容易产生冲突。
- 公共文件(`project.godot`、`autoload/`、`data/` 下的共享配置)改动前必须先和团队沟通。
- 拿不准谁负责的区域,先问,不要闷头改。

---

## 五、改动后必须自测

- `tests/` 目录下有针对物理交互的测试场景(如箱子、碰撞、敌人推箱),**改动相关系统后必须跑一遍**,确认没有回归。
- 关卡改动(地形、机关、敌人摆放)必须自己在 Godot 里实际玩一遍再提交。
- 测试不过就不允许提 PR,先修好再说。

---

## 六、冲突处理

1. `git pull --rebase` 报 conflict 时,不要慌,也不要乱删内容。
2. 打开冲突文件,把 `<<<<<<<` / `=======` / `>>>>>>>` 标记之间的内容整理成正确结果,**保留双方都需要的部分**。
3. 解决后执行 `git add <文件>`,再 `git rebase --continue`,继续后续操作。
4. 自己拿不准怎么合并时,**把冲突文件内容发到群里**,大家商量后再改。

---

## 七、禁止提交的内容

- `.godot/` 目录(Godot 自动生成的缓存,已被 .gitignore 忽略,不要手动 add)
- `*.zip`、备份文件、本地临时文件、调试输出
- 本地私有的配置文件(如导出密钥等)

提交前养成 `git status` 检查的习惯。

---

## 八、常见报错排查

| 报错 | 原因 | 处理 |
|---|---|---|
| `Permission denied` / `403` | 账号未被邀请,或登录了错误的账号 | 确认使用被邀请的账号,检查 Git 凭据 |
| `Updates were rejected` | 远程有新提交,本地分支落后 | 先 `git pull --rebase`,再 `git push` |
| push 到 `main` 被拒绝 | 远程 `main` 有新提交,本地落后 | 先 `git pull --rebase`,再 `git push`;**注意**:本仓库 `main` 无强制保护,拒绝通常只是"远程有新代码"而非权限问题 |
| PR 显示 "Can't automatically merge" | 你的分支与 main 有冲突 | 本地 `git pull --rebase origin main` 解决冲突后 push,PR 自动更新 |
| 克隆时 404 / 无权限 | 未接受邀请,或账号不对 | 检查邀请邮件,确认登录账号 |
| 场景打不开 / 文件丢失 | 用了未合并的旧分支 | pull 最新 main,不要保留本地旧分支 |

**绝对禁止**:未经团队同意使用 `git push -f`(强推),它会覆盖别人的提交。

---

## 九、负责人的额外职责(仓库 owner)

- **及时处理 PR**:当天提交的 PR 当天或次日 review 完,别让合作者干等。
- **定期检查提交记录**:每周至少一次 `git log --oneline -20` 查看谁提交了什么,发现违规(直接 push main、夹带 `.godot/`、大文件、乱写提交信息)立即要求修正。
- 严格把关 `main`:只合并验证过、符合规范的改动,保持主体稳定。
- 发现有人提交了 `.godot/` 或大文件时,提醒并协助清理。
- 每周至少回顾一次合并记录,指出问题、总结改进点。
- 维护本文件,根据团队实际遇到的新问题持续补充。
